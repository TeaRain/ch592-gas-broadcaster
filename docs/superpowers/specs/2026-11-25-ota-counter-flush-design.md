# OTA 前保存燃气计数设计

## 背景与目标

2026-11-26 自然窗口把设备从 1.5.0 自动升级到 1.6.1 后，原始计数从 4.04 m³ 回退到最后一次持久化的 3.95 m³。固件每 100 个计数（0.1 m³）保存一次，而 OTA 请求路径没有保存 RAM 中不足 100 个计数的余量。

发布 1.6.2，确保每次写入 OTA 请求记录前先调用现有 `SaveToDataFlashNow()`，使手动 B、三天定时窗口和普通模式远程唤醒都保存当前计数。保持周期保存阈值、采样、累计、BTHome、OTA 协议和 IAP 行为不变。

## 方案

在共享的小型 `ota_entry_policy.h` 中定义 `OtaEntryFlushBeforeRequest(save, write_request, reason)`，先执行保存回调，再按原 reason 写请求。现有 `OtaMode_WriteRequest()` 使用该生产助手，因此 `OtaMode_Request()` 和 `OtaMode_RequestScheduled()` 都自动获得相同行为。主机 C 测试用事件记录回调验证保存严格先于写入、各执行一次且 manual/scheduled reason 不变；生产代码复用同一助手，不做源码文本匹配。

考虑过在各复位点分别添加保存调用，但容易漏掉后续入口，也会让远程延迟复位与立即复位产生重复实现。共同 OTA 请求入口覆盖更完整，改动更小。

## 边界与实机限制

- `SaveToDataFlashNow()` 保持现有 void 接口和三次写后校验重试，不扩展错误处理协议。
- 不修改 HA 校准值；当前 0.09 m³ 回退需用户按机械表实际读数重新校准。
- 1.6.1 本身没有此修复，从 1.6.1 升到 1.6.2 时仍可能丢失最后不足 0.1 m³ 的余量；避免再次丢失需按 B 先保存再进入 OTA，或升级后重新校准。
- 本轮只发布固件，不触发设备 OTA。构建、自动化测试和独立审查不能替代修复后的实机保存验证。
